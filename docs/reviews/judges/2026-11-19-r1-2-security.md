I found two high-severity contract bugs, and both are reproduced. Holdfast at 156e015 breaks two of its main promises: that the phone can only spend the allowance, and that replacing a guardian takes 7 days. Medium findings include a robber being able to burn a frozen vault down to fees, and the duress screen giving away the vault address.

**Repro:** my tests are in `/tmp/judge2/test/audit/exploits.test.ts` and `/tmp/judge2/test/audit/exploits2.test.ts`. Run them with `cd /tmp/judge2 && npx vitest run test/audit --reporter=verbose`; all 8 pass, each one an exploit that works. The project's own 101 tests pass and `npm run build` works. The live `/real/` bundle matches a local build of 156e015 except for the compile timestamp. Everything ran on CashScript's mock network; nothing was sent on mainnet or chipnet.

## Stage 2: compared with the docs and earlier reviews

I found no earlier review file in the repo or its history. The only past-review material is the three "Blocked" attacks on /under-the-hood/.

- **H1 is new.** It is an unfinished fix of the third listed attack ("a merge can only go back into the vault"). It breaks the Guardians page ("7 days to remove a guardian, so a thief can't do it quietly"), the FAQ, and README step 7. The README and FAQ do admit that phone + home code looks like the owner, but with a guardian the site promises a 7-day public wait. I don't agree with accepting this.
- **H2, M1, M2 are new.** Design choice D ("Fees come from the vault, each spend caps its own fee") is the cause. It contradicts "the phone can spend only the allowance", the FAQ line "It doesn't change what they can take", and "A guardian turns on you: they can take nothing".
- **M4 is new** and contradicts the Guardians page.
- **M5, M6, L1-L6 are new.** The duress view showing only the allowance is intended; leaking the address through Receive is not. Single-server trust is not mentioned anywhere.
- **Already accepted, and I agree:** a level-2 freeze doesn't stop releasing a withdrawal whose wait is over; money already sent can't be reversed; phone + home code with no guardian is full control; no outside audit.

## Checked and believe sound

- Every main-vault function checks that input 0 is the minting vault coin and runs at index 0. The functions for withdrawals, tickets and deposits can't be used on the vault coin, and the reverse also holds.
- Every function except `recover` and `evict` fixes the number of outputs, so no extra or fake vault coin can be minted. CashTokens doesn't allow minting new fungible tokens.
- `release` and `releaseFast` pay only the recorded recipient and burn the token.
- Duress (panic key) can only set level 1, and only from level 0. Strangers can't merge or freeze.
- Waits use the coin's own age (relative timelock), and block counts are limited to 1-65535 in the vault code check.
- Spent-counter encoding has no overflow within the allowed ranges, and negative amounts are rejected.
- `decodeVaultCode` checks every field; the guardian and home-code screens check that the key matches the vault.
- On-screen text in the real app goes through `esc()`, and the demo escapes its inputs. I found no XSS.
- The app checks that the connected wallet's key is the vault's owner key.
- Security headers (`X-Frame-Options DENY`, `frame-ancestors 'none'`, `nosniff`, HSTS) are set on the live site.
- The compiled artifact matches `contracts/Holdfast.cash`.

My suggested order: fix H1 and H2 first (both one-line or few-line contract changes), then M1, M2 and M4. A contract fix changes the vault address, so the existing mainnet vault and its proof transactions would need to be redone on the new contract.
