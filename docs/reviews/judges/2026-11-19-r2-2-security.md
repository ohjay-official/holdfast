# Holdfast security audit (review 2, strict), commit 50d2e2d

**Scope and method.** I cloned the repo to /tmp/judge2b at 50d2e2d. In stage 1 I read `contracts/Holdfast.cash`, `src/vault.ts`, `src/real/{core,main,wallet}.ts` and `src/provider.ts` before looking at any docs or earlier reviews. Stage 2 compared what I found with the README, the site pages and `docs/reviews/judges/*`.

- `npm install` and `npm test` gave 114 passed and 1 failed. The failure is a flaky test (I5).
- The compiled `src/Holdfast.artifact.ts` bytecode matches a fresh `cashc` compile of `contracts/Holdfast.cash`.
- All my reproductions are in `/tmp/judge2b/test/zz-audit2b.test.ts`. Run them with `cd /tmp/judge2b && npx vitest run test/zz-audit2b.test.ts --silent=false`. All 4 pass, and each passing test is an exploit that works.
- Everything ran on CashScript's MockNetworkProvider. CashScript enforces the 1 sat/byte minimum fee there, so the fee numbers are realistic.
- Nothing was sent on any network. Live checks were read-only: curl for headers and one Blockchair lookup. The Blockchair API then rate-limited this IP.

## Stage 2: against the docs and earlier reviews

- **M1 is new.** It gets around the r1 M2 fix ("every approval must change something") by alternating states. It contradicts Under the hood ("Burning a frozen vault… Blocked") and `Holdfast.cash:18`. With no guardian, the README does admit that a coerced home code means "a full freeze and your normal wait". It never says the robber can burn the whole vault during that wait. I don't agree with accepting this.
- **M2 is new.** It is a side effect of the r1 M6 fix (union of two servers). That fix covered *hiding* a coin, not *adding* one.
- **M3 is partly accepted** (README :42 and /security/ say v1 is kept). I don't agree with offering no in-app warning or move flow while known theft bugs remain in v1.
- **L1 is half-accepted.** README :70 says merges "pay up to 4,000 from the coin merged in", and `test/attacks.test.ts:107` allows it. The contract comments and the "never move or burn more than the allowance" wording still overclaim. Either fix it or change the wording.
- **L2 is the leftover of r1 L5,** which was mostly fixed. I accept it if the site says PINs only guard the screen.
- **L3 and I4 are new.** I1 is intended and accepted, and I agree. I2, I3 and I5 are new.
- **The r1 fixes check out in v2:** H1 (`merged()` pins the commitment), H2 (payment == amount, fee counted), M1 (input 1 must be at the vault, fee from the merged coin, no phone or panic merge at level 2), M2 (approval must change state), M4 (only the home code merges a ticket), M5 (the decoy Receive shows the wallet address), L1 (500-step loop), L2 (recovery flags only at level 2, cleared on unfreeze), L3 (home key cleared on lock and on navigation), L4 (guardian checked against own keys). The project's attack tests cover these and they pass.

## Checked and believe sound

- Each main-vault function requires input 0 to be the category's minting coin at `activeInputIndex == 0`. The non-main functions (`merged`, `ticket`, `release*`, `approveFast`) can't be satisfied by the vault coin, and the only function a coin as input 1 can use in a vault transaction is `merged()` (or `ticket()` in `evict`).
- Every function except `recover` and `evict` (home-key exits) fixes the output count and token categories, so no extra minting NFT, fake ticket or fake fast withdrawal can be minted. `approveFast` is the only path to `0x5001`, and it needs the guardian.
- No arithmetic problems: `spent` is an 8-byte padded number that is only written through `toPaddedBytes`, `fee >= 0`, `amount > 0`, `used >= amount`, and spend can't reach negative or overflow values.
- `release` and `releaseFast` pay only the recorded recipient, burn the NFT and cap the fee at 2,000. Coins of a foreign category at the address can't use them, because `category` is a constructor parameter.
- No-guardian `recover` needs level 2 plus `this.age >= waitBlocks` on the vault coin. During level 2 only home or guardian keys can touch the vault coin.
- Category byte order (`categoryForContract` reverses it), genesis at input 0, creation fee output, and the creation record saved before signing.
- Web: the CSP on the live site is `script-src 'self' 'wasm-unsafe-eval'` with an allowlisted `connect-src`; `frame-ancestors 'none'`, XFO DENY, HSTS and nosniff are present. All rendered chain and user strings go through `esc()` or are hex. No secrets are in the bundle. No server or API surface exists.
- WizardConnect: the guardian code check binds the vault to the connected wallet's receive/0 key, and the guardian key can't equal the owner, home or panic key at creation.
- AI parts: none at runtime.
